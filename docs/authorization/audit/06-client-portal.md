Scope: `sanctum-backend` (read-only review).

## 0. Actor types in this area today

| Actor (today) | How it authenticates | Principal in code | Where the scope comes from |
|---|---|---|---|
| **Client user (password login)** | `/auth/login`. JWT access token (15 min) + refresh token (30 days) with `role:'client'` and `clientId` | `req.auth` → `req.clientCtx` (`middleware/client.ts`) | `users.clientId` (the brand). `client_user_projects` rows limit it to those projects. **No rows means ALL of the brand's projects.** |
| **Portal-link session user** | `POST /portal/session` swaps a share token for real client JWTs | A synthetic `users` row, one per brand: `portal.<clientId>@portal.sanctum` | Brand only. It never gets `client_user_projects` rows, so it always sees every brand project. |
| **Portal token (share link)** | `Authorization: Bearer pzt_…`. The sha256 hash is looked up in `portal_tokens` | `req.portal = {tokenId, agencyId, clientId}` | Brand only. The token has no project, permission, or role fields. |
| **Anonymous document token** | Raw `proposals.token` / `agreements.token` in the URL path | None (the token itself) | A single object. Stored **in plaintext**, never expires, cannot be revoked. |
| **Portal socket** | `handshake.auth.portalToken` | `socket.data.kind='portal'` | Joins the `portal:<clientId>` room. |
| **Client-user socket** | Cookie or `auth.token` JWT | `socket.data.kind='user'` (the same path staff use) | userRoom + thread rooms. |

Client "approver/reviewer" today is `clients.portalRole`. It is **one value per brand**, not per login or per link, and only post approval checks it.

### 1c. Anonymous document tokens (`src/routes/proposals.ts`, `src/routes/agreements.ts`)
Gates: only `globalLimiter` (no `portalLimiter`, no auth). The token is `newOpaqueToken().raw` (`pzt_` + 24 random bytes), generated **when the record is created (even as a draft)** (`proposals.ts:345`, `agreements.ts:280`). It is stored **in plaintext** in `proposals.token` / `agreements.token`, has no expiry column, no revoke, and no rotation on resend. It is returned to staff (`serializeProposal`/`serializeAgreement`) and to client users (#20-25).

## 2. Cross-cutting findings

### 2.1 Per-brand vs per-project leaks (project-restricted client users)
`ClientContext.projectIds` is honoured **only** by `/client/projects*` (#8-10) and partially by files/folders. Everything else filters by `clientId` alone:
- Calendar/posts/comments/decisions (#16-19): `content_posts` has **no `projectId`**, so these cannot be project-scoped today.
- Proposals (#20-23): the `proposals` table has **no `projectId`**.
- Agreements (#24-26): `projectId` exists but is ignored.
- Invoices (#27-28): `projectId` exists but is ignored, and out-of-scope project names leak.
- Files/folders (#11-15): the `clientId OR projectId∈scope` predicate leaks brand-tagged docs belonging to other projects. Uploads can inherit out-of-scope projects through folders.
- Fail-open scope: zero `client_user_projects` rows means ALL projects (`client.ts:39-54`). Deleting the last scoped project (FK cascade) silently widens access.
- Stale scope: `requireClientAuth` never re-checks `projects.clientId = ctx.clientId` for explicit rows (validated only at invite time, `users.ts:654-668`).

### 2.2 Approver/reviewer model
`clients.portalRole` (brand-wide) is enforced **only** on post approval (#4, #19). It is not applied to proposal accept/reject (#22-23), agreement signing (#26), invoice viewing (#27-28), uploads (#13-15), or comments. Every login and every share link of the brand therefore has identical power. **Recommendation:** replace it with client-side roles (permission bundles) assigned per client user and per portal link:

| Client role (bundle) | Permissions |
|---|---|
| `client_owner` / Client Admin | portal.view_projects, portal.view_project_team, portal.view_files, portal.upload_files, portal.view_calendar, posts.view_comments, posts.comment, posts.request_changes, posts.approve, proposals.view, proposals.respond, agreements.view, agreements.sign, invoices.view |
| `client_approver` (content) | portal.view_calendar, posts.*, portal.view_files, portal.view_projects |
| `client_reviewer` | portal.view_calendar, posts.view_comments, posts.comment, posts.request_changes, portal.view_files, portal.view_projects |
| `client_finance` | invoices.view, agreements.view, proposals.view |
| `client_viewer` | view_* only |
| Share-link grant (default) | portal.view_calendar, posts.view_comments, posts.comment, posts.request_changes (+ posts.approve only if explicitly granted). **Never** proposals.respond / agreements.sign / invoices.view / upload unless explicitly granted. |
| Document link (anonymous) | `proposals.view_public` + `proposals.respond` on `object:proposal:{id}`; `agreements.view_public` + `agreements.sign` on `object:agreement:{id}` |

Scopes: `client:{clientId}` (mandatory for every client actor) plus an optional `projects:[…]` subset with an explicit `allProjects` boolean (no "empty means all"). The engine evaluates `permission ∈ actor.bundle ∧ object ∈ scope ∧ objectPolicy(object, actor)`.

### 2.3 State-machine object policies missing
- Proposal accept/reject (client #22-23, public #30-31): there is no `status ∈ {sent, viewed}` guard and no `validUntil` check. Accepted or converted proposals can be rejected, and drafts, expired, or rejected ones can be accepted.
- Agreement sign (client #26 has **no guard at all**; public #33 only blocks signed/active): drafts, terminated, and expired agreements can be signed, and client users can re-sign and overwrite existing signatures.
- Posts via `/client` (#17-19) skip the `archivedAt` and visible-status checks that `/portal` applies (partially).

### 2.4 Data exposure
- Staff PII to clients: staff user ids + full names + designation (#9, #10). Staff-authored comments are always client-visible (no internal flag on `post_comments`).
- Money: proposals (#20-21), agreements (#24-25), invoices incl. bank details and payment references (#27-28), all brand-wide.
- Secrets: public `token` returned by `/client/proposals*` and `/client/agreements*`. Proposal/agreement tokens are stored in plaintext.
- Anonymous: signed-agreement link exposes signer IP/email/signature + client billing address + contact email (#32). The proposal link exposes staff `createdBy` and `leadId` (#29).

### 2.5 Identity / credential integrity
- `mintClientPortalLogin` targets the **oldest** client user of the brand and **overwrites its email + password + status** (#38, #40a, #40b). Sending a document-mode proposal/agreement can therefore hijack a named contact's account or re-enable a disabled one.
- Agency staff can choose or know client passwords (#38), which weakens e-signature non-repudiation (#26).
- Email uniqueness is per agency, but login is global `lower(email)` + `limit(1)`.
- Client comments are mirrored into staff threads authored by an owner user (#5, #18).
- `actorLabel` on share-link actions is free text (#4, #5).

## 3. Portal token lifecycle (as implemented)

1. **Create**
   - `POST /clients/:id/portal-tokens` (owner/admin): `newOpaqueToken()` → `pzt_<24B base64url>`. It stores `sha256(raw)` in `portal_tokens.token_hash`, plus label, `createdBy`, and `expiresAt` (only if `expiresInDays`, max 365; **default null = never**). Returns raw once. Audit `portal_token.create`.
   - `POST /clients/:id/send-welcome` (owner/admin): same insert with `label:'welcome'` and **no expiry**. Emails `${frontend}/portal/<raw>` via `sendPortalWelcome`. Audit `client.send_welcome` (no token id in the audit).
   - Seed data also creates tokens (`seed.ts`).
2. **Email / distribute:** only send-welcome emails a link. Tokens from `portal-tokens` are copied by staff manually. The raw token sits in the URL **path** (`/portal/<token>`, `/access/<token>` on the web), which exposes it to access logs, browser history, referrers, and email link scanners.
3. **Resolve (REST):** `requirePortalToken` reads `Authorization: Bearer` (a `:token` path param fallback exists but no portal route defines one). It hashes the token and looks it up: missing → 404, `revoked` → 410, expired → 410. Then it updates `lastUsedAt` (fire-and-forget) and sets `req.portal={tokenId, agencyId, clientId}`. It is re-checked on **every** `/portal/*` request, so revocation is immediate for token-only use.
4. **Resolve (socket):** the same check runs **once at handshake**. A revoked token's socket stays connected until it disconnects.
5. **Exchange to session:** `POST /portal/session` → `ensurePortalUser` (one synthetic `role:'client'` user per brand, email `portal.<clientId>@portal.sanctum`, random unusable password, no project rows = all projects). It signs an access JWT (`sub`, `agencyId`, `role:'client'`, `clientId`; 15 min) and a refresh JWT (`sub`, `agencyId`; **30 days**). **Neither carries `tokenId`, a session id, or `jti`.** No audit event. The web `/access/[token]` stores these and routes to `/client` (full client portal).
6. **Refresh:** `POST /auth/refresh` verifies the refresh JWT signature, then `users.status==='active'`, then issues a fresh pair (a new 30-day refresh each time). No server-side session store and no reuse detection. `/auth/logout` only clears cookies, so Bearer-held refresh tokens remain valid.
7. **Revoke:** `POST /clients/:id/portal-tokens/:tokenId/revoke` sets `revoked=true, revokedAt`. Effects:
   - `/portal/*` with that token → 410 (immediate).
   - Sessions previously exchanged from it → **unaffected** (the access token lives up to 15 min, then refresh keeps rotating indefinitely).
   - Portal sockets → stay connected.
   - Other links of the same brand share the same synthetic user, so there is no per-link session kill. The only lever is disabling the synthetic user (kills every link's sessions, and `POST /clients/:id/portal-login` can re-enable it if it is the oldest client user).
   - Public proposal/agreement tokens obtained through that session (#20-25) → **remain valid forever**.
8. **Expiry:** `expiresAt` is enforced on REST resolve and socket handshake only. It does not cap the exchanged session. Welcome tokens never expire. There is no cleanup job and no rotation.

### 3.1 What a proper revocation model needs
1. **A first-class `portal_link` actor, not a synthetic user.** Sessions minted from a link have `actorType:'portal_link'`, `actorId=tokenId`, and grants copied from the token (`permissions`/role bundle, `allProjects`, `projectIds`). Audit records `tokenId` (+ optional verified `actorLabel`).
2. **A server-side session table** (`auth_sessions`: `id (sid)`, `actorType`, `userId?`, `portalTokenId?`, `agencyId`, `clientId`, `createdAt`, `expiresAt`, `lastSeenAt`, `revokedAt`, `refreshHash`/family id).
   - Access + refresh JWTs carry `sid` (and `tid` for link sessions).
   - `/auth/refresh` requires the session row to be active and, for link sessions, the linked token to be active (not revoked, not expired, the brand not archived). It rotates the refresh token with reuse detection.
   - Session `expiresAt = min(now + policy TTL, token.expiresAt)`, with a shorter TTL for link sessions (e.g. 24 h to 7 d).
3. **Revoke cascades:** revoking a token → `UPDATE auth_sessions SET revokedAt WHERE portalTokenId=?` → `io.in('session:<sid>')` / `io.in('portal-token:<tokenId>').disconnectSockets(true)`. Disabling a client user, removing project scope, changing `clientId`, or archiving the brand → revoke that user's sessions the same way.
4. **Short-lived access tokens + a revocation check:** keep 5-15 min access tokens. For link actors, optionally check `sid` against a cached revocation set per request (a cheap in-memory/LRU check, invalidated on revoke).
5. **Token hygiene:**
   - Mandatory `expiresAt` (default e.g. 30 days, max 90) on all share links, including welcome links.
   - Optional single-use exchange (`consumedAt`) for welcome links.
   - Put the token in the URL fragment (`/access#t=…`) or exchange it immediately and strip it from the URL.
   - Record `createdBy`, the grants, and the recipient email.
   - Rotate and invalidate prior links on resend.
6. **Document links:**
   - Move `proposals.token`/`agreements.token` into a hashed `document_links` table (`objectType`, `objectId`, `tokenHash`, `permissions`, `expiresAt` defaulting to `validUntil`/`expirationDate`, `revokedAt`, `consumedAt` for sign/accept).
   - Mint the link only on `send`, never at draft creation. Revoke it on resend or when the status changes to terminal.
   - Never return raw tokens in any list API.
7. **Credential provisioning:** replace "reset the oldest client user" with explicit per-user invites (set-password link, no staff-chosen passwords), scoped to a client role bundle and project set, and never implicitly re-enable disabled users.
